# Services and Commercial Support

AIC is open and commercially usable under Apache-2.0.

That means teams can adopt it freely, including in commercial products and internal platforms. The business opportunity for AIC is not selling permission to use the code. It is selling expertise, support, implementation speed, and eventually hosted or premium capabilities around the ecosystem.

## Immediate Monetization Paths

- paid onboarding for teams making apps AIC-ready
- implementation services for React, Next.js, and Vite apps
- agent-readiness audits for risky workflows and production UI flows
- custom MCP integrations for Claude, Cursor, Codex, and internal agent stacks
- behavior-assurance sprints that define contracts for consequential operations and execute success, denial, confirmation, failure, and recovery scenarios
- cross-surface parity work for human UI, WebMCP, MCP, and API entrypoints
- conformance-pack selection, reviewed application bindings, custom pack authoring, and regression profiles
- CI proof gates, protocol evidence plans and adapters, cumulative assurance policy, and proof-retention policy
- deployment of the self-hostable remote runner with public-network controls, minimal secret references, and exact canary grants
- issuer-key setup, deployment-bound signed claims, scheduled dual-signed rotation, trust-store policy, and registry integration
- compatibility-vector integration for third-party verifier implementations
- signed reference transparency-index integration and external receipt metadata binding
- consumer-owned Trust Fabric policy design and `@aicorg/rely` pre-execution integration for agents, gateways, WebMCP/MCP clients, HTTP mutations, and release systems
- pinned, fail-closed `actions/aic-rely` rollout with workflow protection, trusted-clock/replay policy, identity binding, and decision retention
- self-hosted `@aicorg/reliance-server` deployment, public-artifact review, portable snapshot export, and independent-mirror setup
- WebMCP implementation and compatibility work that remains native-first and routes to shared domain operations
- private support retainers and faster response channels
- training, architecture reviews, and integration workshops

## Later Monetization Paths

- hosted evidence collection, resolver/history, policy evaluation, and contract review workflows that preserve local verification and exportable records
- managed bootstrap and review pipelines
- independently operated managed evidence runners and reachability checks
- standardized/provider-verified transparency receipt integrations and globally witnessed history
- independent conformance certification support
- enterprise support, SLAs, and compliance packaging
- premium integrations or managed cloud features

## Attribution Request

Apache-2.0 does not let this repository force product-level branding or public acknowledgment from every user.

What the project can do:

- preserve attribution through the repository and NOTICE file
- keep the AIC name and branding separate through trademark and naming policy
- ask adopters to mention AIC voluntarily

If you use AIC in a public product, please mention that your app is "built with AIC" and link back to the repository when practical:

- Repository: https://github.com/VPAI-Grok/AIC
- npm scope: `@aicorg/*`

## Positioning

The recommended strategy for AIC at this stage is:

- maximize adoption with Apache-2.0
- monetize implementation, support, and hosted value
- keep contracts, schemas, the verifier, and local evidence collection open
- keep conformance packs, evidence plans/adapters, policy, compatibility vectors, signing, verification, trust stores, registries, the reliance SDK/CLI/action, mirrorable resolver format, and reference transparency formats open
- build the official ecosystem around independently operated runners, portable proof, reusable packs, consumer-owned fail-closed policy, external agent enforcement, and independently mirrorable discovery
- use WebMCP as a native execution layer while AIC remains the protocol-neutral assurance layer
- never imply that an issuer-signed claim independently proves production reachability or compliance certification
- never make an AIC-hosted resolver, dashboard, or key an implicit universal trust root

The repository now contains the open Trust Fabric SDK, canonical decision formats, CLI command, bundled action, and reference resolver. The npm packages are published under the `alpha` tag, but they are not AIC-operated hosted services. AIC currently has no verified external adopter, no external enforcing agent/gateway consumer, no independently operated AIC-hosted runner, no public resolver with an independent mirror and durable history, no globally witnessed transparency service, no provider verifier for external receipt metadata, and no certification program. Those are future operational and ecosystem opportunities, not shipped-service claims.
